# Item Menu Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One "..." menu on every list item (bottom sheet on narrow/touch, popover on wide pointer screens) with Play (clear queue, add, play), Add to queue, and per-kind extras, backed by a background `POST /api/enqueue`.

**Architecture:** A new `internal/enqueue` service does the multi-step cliamp work (clear-then-play, track-by-track appends over albums/playlists/artists) in the background and reports progress; the server exposes it with SSE `enqueue` events. The page gets one menu component fed by a pure action list per item kind.

**Tech Stack:** Go stdlib; vanilla JS/CSS.

**Spec:** `docs/superpowers/specs/2026-11-22-item-menu-design.md` (amended: **no 1000-track cap** — everything is appended, with progress and a Stop button).

## Global Constraints

- Play = clear queue + add + start playing. Track: `queue.clear` then `track.play`. Album: `provider.load_album {provider, album}`. Playlist: `provider.load {provider, playlist}`. Artist: `queue.clear`, `track.play` the first track, `queue {path}` the rest.
- Add to queue = `queue {path}` per track, strictly sequential and in order, no `if_revision`, no cap, no concurrency.
- Listings are paged (`limit` 200) via `provider.album_tracks`, `provider.tracks {playlist}`, `provider.artist_albums`.
- A track's path from the page must be a stream URL the bridge handed out (scrubbed and remembered) or a track the bridge knows (`HasTrack`); else 403. Paths are restored to the real URL before any cliamp call.
- One enqueue at a time (second -> 409); `POST /api/enqueue/cancel` stops after the current item.
- SSE `enqueue` events `{state: running|done|failed|cancelled, done, total, error?}`, throttled to at most one per 200 ms plus the final one. Errors are the cliamp error detail only; never URLs or credentials.
- Radio Play uses the existing allowlisted `provider.load` via `/api/command`.
- Menu breakpoints: sheet below 600 px or on a coarse pointer, else popover. Accessibility per spec (`role=menu`, arrows, Home/End, Enter/Space, Escape returns focus).
- Existing gates stay green: `make test`, `go test -race ./...`.

## Review Focus

- A 12,000-track playlist: sequential appends, progress events, Stop works, nothing held in the HTTP request. (Task 1, 2)
- An artist with many albums: order of tracks preserved across albums. (Task 1)
- Two quick Add-to-queue taps: the second gets 409, the first is not disturbed. (Task 1, 2)
- cliamp error mid-way: state `failed`, events stop, the worker exits and a new enqueue can start. (Task 1)
- Menu on a row near the bottom/right of the screen: popover flips and stays inside the viewport; Escape returns focus to the "...". (Task 3, 4)

### Task 1: enqueue service

**Files:**
- Create: `internal/enqueue/enqueue.go`, `internal/enqueue/enqueue_test.go`

**Interfaces:**
- Consumes: `ipc.OpRunner`.
- Produces:
  ```go
  type Request struct { Kind string /* track|album|playlist|artist */; Provider, ID, Mode string /* play|append */; Track map[string]any }
  type Event struct { State string `json:"state"`; Done int `json:"done"`; Total int `json:"total"`; Error string `json:"error,omitempty"` }
  var ErrBusy, ErrInvalid, ErrUntrusted error
  type Service struct{ /* unexported */ }
  func New(r ipc.OpRunner, restore func(string) string, known func(string) bool, emit func(Event), now func() time.Time) *Service
  func (s *Service) Start(req Request) error   // validates, then runs in the background; ErrBusy while another runs
  func (s *Service) Cancel()
  func (s *Service) Wait()                     // for tests: blocks until the running job ends
  ```
